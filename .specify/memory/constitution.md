# VibeTags Constitution

The rules a Spec Kit plan for this repository is written under. It is deliberately short, and it
points at the authoritative documents rather than restating them: a constraint copied into a second
file is a constraint that can drift from the first, which is a defect shape this project tracks in
its own output (see issue #763) and will not reproduce in its own governance.

## Core Principles

### I. The Tier-1 invariants are supreme

`CLAUDE.md` enumerates the Tier-1 invariants, each naming the check that enforces it, and
[docs/LOAD-BEARING.md](../../docs/LOAD-BEARING.md) gives the reasoning behind every one. They are
not repeated here, and a number is not quoted here, because both would then exist in two places.

A spec that touches an invariant names it and says how the plan keeps it. A plan that cannot keep
one is not a plan; it is a proposal to change the invariant, which is a separate decision taken
before the work starts, not discovered during it.

### II. A claim is measured, not asserted

"Faster", "smaller", "equivalent" and "no behaviour change" are claims, and this repository's own
issue tracker is full of findings recorded as *"Not measured. Scaling argument from reading."*
A plan states how each claim will be measured, and the result reports the number, both sides of the
change, from a real build. Reading the code is how a claim is formed, never how it is settled.

### III. A test earns its place by failing

A test that has never been seen to fail proves that the code runs, not that the test detects
anything. Write it before the fix where that is possible; where it is not, break the fix
deliberately once and confirm the test goes red, and say which of the two happened. A test whose
assertions stay green while the defect is present is worse than no test: it reports safety that is
not there.

### IV. A skipped gate is not a passed gate

Green, skipped, unavailable and not-run are four different results and are reported as four
different results. Some checks in this repository report success while doing nothing (issue #632),
and a build log that says `Skipped` next to a gate is evidence about the gate, not about the code.
Absence of findings is never evidence of correctness.

### V. Generated output is regenerated, never edited

Anything between `VIBETAGS-START` and `VIBETAGS-END`, and every file listed in the platform
registry, belongs to the generator. Content outside those markers is the author's and must survive
regeneration untouched. A change that moves generated bytes regenerates them in the same commit —
including `.vibetags-locks`, which records source positions and therefore moves when unrelated
lines above a locked element do.

### VI. A lock is escalated, never worked around

An element in `<locked_files>` is not edited, and its guard is not loosened to make a change fit.
Where a plan needs one to move, it says so and stops there. The `action/locked-files` guard enforces
this on every pull request; the guard is the floor, not the reason.

## Development Workflow

A feature branches from `main`, never commits to it, and opens a pull request that a human merges.
The pull request states what was verified and how, names anything it left undone, and opens an issue
for each deferred item — prose in a merged body is not a backlog, because nobody re-reads it once
the branch is gone.

The pipeline is followed after every push until it is green. A local pass is not a substitute: CI
runs a different OS, a different JDK and a different contention profile, and the failures that only
appear there are the ones worth having.

## Governance

This constitution governs Spec Kit artefacts — `spec.md`, `plan.md`, `tasks.md` and the commands
that read them. It does not override `CLAUDE.md`, which every agent session loads and which remains
the operative instruction file; where the two ever disagree, `CLAUDE.md` wins and this file is
wrong and gets fixed.

Amending it means saying which principle changed and why, in the commit that changes it.
