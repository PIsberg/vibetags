AI Context & VibeTags3
Fundamentals

AI context — and why it matters

Context is everything the model can see when it answers: your prompt, the open files, tool output — and the instruction files the agent loads before you type anything.

Those instruction files are the only part you control declaratively. They're also the only part that is always in the window, on every single request, whether or not it's relevant.

Three properties decide whether context helps

  • Presence — is the rule in the window at the moment the agent is about to break it? A rule that loads after the damage is done has failed.
  • Accuracy — does it still describe the code? Stale context is worse than no context: it's confidently wrong.
  • Density — five critical rules buried in 500 lines of boilerplate get treated like 500 lines of boilerplate. Attention is a budget.

The always-loaded budget

A root CLAUDE.md is prepended to every request in the session. Whatever is in it competes with your actual question for the model's attention — and grows linearly with the codebase unless something stops it.

The two failure modes

Too little — the agent invents conventions, refactors load-bearing code, logs PII.

Too much — the safety rules are diluted to noise and the agent ignores all of them equally.

A rule that only loads after the agent opens the file it protects has already failed.

What the agent does

It reads the code, infers conventions from whatever files it happens to open, and fills the gaps with the average of GitHub.

Typical outcomes

  • Adds a log.debug("card={}", cardNumber) while debugging CardVault.
  • Simplifies the "redundant" idempotency check in RefundService.
  • Changes double → BigDecimal in a public signature to "fix" currency handling, breaking two consumers.
  • Introduces a new HTTP client library because it prefers that one.

Verdict: fast, plausible, and occasionally catastrophic. Every constraint has to be re-typed into the chat, by every developer, every session.

- Never log card numbers or passport data

Tier 1 = project scope

Where it goes: CLAUDE.md in the repository root — the reactor root in a multi-module build. Loaded into every request in the session, whatever you're working on. (There is a personal global file above this one. We come back to it shortly.)

A real improvement

Project-wide conventions stated once, in version control — every developer's agent now sees the same thing. The single highest-value hour most teams never spend.

Where it starts to strain

  • Everything is global. A rule about the fare cache is loaded while you work on refunds.
  • It's prose about code. "RefundService's retry logic" — which method? Still there after the class was split?
  • It only serves Claude. Your colleague on Cursor gets none of it.
  • Nothing keeps it true. The file and the code drift the moment someone merges.

Verdict: right idea, wrong granularity, no enforcement.

Tier 2 = module scope

Where it goes: CLAUDE.md in each module root, next to that module's pom.xml — payments/CLAUDE.md, search/CLAUDE.md. Loaded when the agent is working inside that module. Domain rules stop polluting the Tier 1 budget.

Better still

Ownership now matches team boundaries: the payments team owns the payments rules. Review is local. The root file shrinks to genuinely cross-cutting policy.

Remaining problems

  • Module is still coarse. payments/ has 80 classes; the agent loads rules for all of them to edit one.
  • Three files to keep in sync — and nothing checks that they agree with each other, or with the code.
  • Still Claude-only. Multiply every file by the number of AI tools in the team.
  • Copy-paste drift between modules is now guaranteed rather than likely.

Verdict: the right shape. Three times the maintenance.

Zoom out · above Tier 1

Three of these layers are invisible to your team

The three tiers we just walked through are the ones that live in the repository. They are not the whole stack. Claude Code concatenates everything it finds, broadest scope first — and only half of it is under source control.

ScopeWhere it livesWho gets itIn git?
Managed policy/Library/Application Support/ClaudeCode/CLAUDE.md (macOS) · /etc/claude-code/CLAUDE.md (Linux, WSL) · C:\Program Files\ClaudeCode\CLAUDE.md (Windows)Everyone in the orgNo pushed by IT

Concatenated, not overridden

Ordered from the filesystem root down to your working directory, so the instruction closest to where you launched is read last. CLAUDE.local.md is appended after CLAUDE.md at each level.

This is where drift comes from

Your colleague's agent behaves differently from yours and neither of you can see why, because the difference is in a file that was never in the repository. "Works on my machine" for prompts.

What to do about it

Keep ~/.claude/CLAUDE.md for genuine personal taste — editor habits, how you like to be spoken to. Anything a reviewer would care about belongs in Tier 1–3, in git. In a monorepo, claudeMdExcludes skips other teams' files; managed policy cannot be excluded.

The pattern
We just reinvented documentation —
with all the same failure modes.

Hand-edited

Every developer maintains their own. Nobody reviews a Markdown file with the care they'd review code.

Inconsistent

Twelve repos, twelve dialects. Copy-paste between modules diverges within a sprint.

Stale on merge

The rule refers to a class that moved two refactors ago. No compiler, no test, no CI check notices.

The rules describe the code. So why are they stored away from the code, in a format nothing can verify?

AI Context & VibeTags10
The proposal

VibeTags — compile your AI config

A compile-time Java annotation processor. You annotate the code; mvn compile regenerates every AI tool's guardrail file. Source-controlled, code-adjacent, CI-enforceable.

Annotate once, all platforms updated

Add @AILocked to PaymentProcessor and every AI tool's guardrail file is regenerated on the next compile. No per-developer copy-pasting across config files.

Derived from the code, not separate from it

Guardrails live next to the code they protect. When the code moves, the rules move with it. Rename the class — the rule follows.

Granular rules keep the always-loaded context slim

Opt a platform's scoped-rules directory in and its aggregate file collapses to an index. Only the safety buckets stay inline; per-element detail loads on demand.

Zero runtime cost

RetentionPolicy.SOURCE annotations are erased at compile time. Nothing reaches the JVM. The annotations artifact has zero dependencies.

CI-enforceable

Opt-in check mode (-Avibetags.check=true) fails the build when guardrail files have drifted from the annotations. The locked-files GitHub Action fails any PR whose diff touches @AILocked code.

Strict opt-in: file presence is the configuration

VibeTags never creates config files on its own. It only populates files that already exist. Create the file to opt in; rm it to opt out and it never comes back.

# opt in to what your team actually uses
touch CLAUDE.md .cursorrules AGENTS.md
mkdir -p .claude/rules .cursor/rules
mkdir -p .github && touch .github/copilot-instructions.md

mvn compile   # VibeTags populates all of them

Generated content lives strictly between <!-- VIBETAGS-START --> and <!-- VIBETAGS-END -->. Your own prose outside the markers is never touched.

Wiring it into the build

<!-- Maven -->
<dependency>
  <groupId>se.deversity.vibetags</groupId>
  <artifactId>vibetags-annotations</artifactId>
</dependency>

<annotationProcessorPaths>
  <path>
    <groupId>se.deversity.vibetags</groupId>
    <artifactId>vibetags-processor</artifactId>
    <version>1.3.5</version>
  </path>
</annotationProcessorPaths>
// Gradle
compileOnly 'se.deversity.vibetags:vibetags-annotations'
annotationProcessor 'se.deversity.vibetags:vibetags-processor'

Keep the processor off compileClasspath — that's what stops slf4j/logback leaking into your code. Kotlin works via kapt or the vibetags-ksp front end.

AI Context & VibeTags17
Enforcement

Generated is not the same as respected

Guardrail files ask an AI tool to keep out. Two CI gates verify nothing slipped through.

Gate 1 · Drift check

Check mode runs the full generation and compares it against what's on disk — writing nothing — and reports every stale file as a compile error. Catches un-regenerated annotations, hand-edited generated blocks, and orphaned rule files.

# .github/workflows/ci.yml
- name: Verify AI guardrails are in sync
  run: mvn -B compile -P vibetags-check
[ERROR] VibeTags: check failed — 3 guardrail
file(s) are out of date with the annotations:
  - CLAUDE.md
  - .cursorrules
  - .cursor/rules/com-example-PaymentProcessor.mdc
Run a normal compile and commit the regenerated files.
Gate 2 · Locked-code PR guard

touch .vibetags-locks and the compile emits JSON Lines — one entry per @AILocked element with its file and line range. The Action rebuilds the PR head and flags three things as inline PR annotations:

  • edits inside a locked line range
  • removal of an @AILocked annotation line
  • deletion of a file that contained @AILocked
- uses: actions/checkout@v6
  with: { fetch-depth: 0 }
- uses: actions/setup-java@v5
  with: { distribution: temurin, java-version: 21 }
- uses: PIsberg/vibetags/action/locked-files@v1.3.5

Only a real annotation counts — @AILocked inside a string literal or comment is ignored. warn-only: true reports without failing while you roll it out.

AI Context & VibeTags18
Honesty

Where it bites

Two silent failures worth knowing

  • JDK 23+ only runs explicitly configured processors. Declare vibetags-processor as an ordinary dependency and the build is green and generates nothing — no error, no warning. Use <annotationProcessorPaths>.
  • A build with nothing to compile never starts javac. An incremental mvn compile skips the processor, so a newly opted-in file stays empty. mvn clean compile.

Gradle check mode has a trap

Check mode runs inside the processor, so it only runs if javac runs — and Gradle skips an UP-TO-DATE compileJava. Without outputs.upToDateWhen { false } the check passes having verified nothing. Maven has no equivalent hazard.

JVM language support

LanguageSupportWhy
JavaFulljavac runs the processor directly
KotlinFullkapt stubs, or the vibetags-ksp front end
GroovyPartialTypes & methods only — groovyc stubs carry no fields, so field-level @AIPrivacy silently does nothing
ScalaJava onlyscalac has no JSR 269 support
ClojureNot possibleNo javac in the pipeline; SOURCE retention can't be expressed

The diagnostic you'll actually use

jbang se.deversity.vibetags:vibetags-cli:1.3.5 doctor

No compile needed. Reports whether the processor is wired in, which platforms are active, unbalanced markers, and exactly which Groovy/Kotlin declarations are being silently dropped. Exit 0 healthy, 1 findings — cheap CI step.

AI Context & VibeTags21
The three artifacts

What actually goes in each file

Each one feeds the next. The discipline is keeping the wrong content out — a tech choice in the spec, or a requirement invented in the plan, is how the chain quietly stops being a chain.

spec.md · what & why
You write it. A product person could read it.
  • The problem, and who has it
  • User stories in priority order
  • Acceptance criteria — observable, testable
  • Edge cases and error behaviour
  • Explicit non-goals
  • [NEEDS CLARIFICATION] markers
Keep out: frameworks, databases, class names, API shapes.
plan.md · how
Agent drafts, you approve. An architecture review on one page.
  • Stack and versions, with the reason
  • Architecture: modules, layering, boundaries
  • Data model and persistence changes
  • API contracts — endpoints, payloads, errors
  • Test strategy: unit / contract / integration
  • Migration, rollout, feature flags
  • Constitution check — where it bends, why
Keep out: new requirements. Those go back to the spec.
tasks.md · in what order
Generated, you scan it. The agent's actual worklist.
  • Setup — scaffolding, dependencies
  • Foundational — blocking prerequisites
  • One phase per user story, in priority order — tests inside the phase, not after
  • Polish — cross-cutting concerns last
  • Dependency order + parallel markers
  • A Convergence section for appended gaps
Keep out: design decisions. A judgement call here is a hole in the plan.
Above all three — constitution.md: project-wide non-negotiables, written once. "TDD, strictly." "Library-first." Every later phase is judged against it.
Repairs go upstream: requirement gap → specify/clarify · design problem → plan · wrong breakdown → regenerate tasks. Never patch downstream and hope.

The locked-files PR guard is human-in-the-loop by force: a diff touching @AILocked code fails the PR and gets an inline annotation. No amount of agent confidence gets past it — someone has to look.

Testing

Where TDD earns its keep with agents

A test is an executable specification. Prose asks the agent to behave; a failing test tells it when it has. Agents happen to be very good at the one thing TDD asks for: make this red test green without breaking the others.

✅ Worth the ceremony

  • Anything the agent will rewrite. @AIContract freezes the signature; the test freezes the behaviour. Together the agent can replace the whole implementation safely.
  • Bug fixes. Red test reproducing the bug → agent makes it green. This is the single highest-yield agent workflow there is.
  • Money, dates, tax, refunds. Edge cases you can enumerate faster than you can describe.
  • Load-bearing code. If @AILoadBearing records why it can't be removed, the test proves it.
  • Public APIs. @AIPublicAPI says additive-only; a contract test enforces it.

❌ Don't force it

  • Spikes and prototypes. That's what @AIPrototype and @AIDraft are for — relax the rules, prevent the leak into production.
  • Layout, wiring, config. A test that asserts the code says what the code says.
  • Third-party integration edges where a recorded contract test beats a mock that agrees with your misunderstanding.

Make it a guardrail, not a wish

@AITestDriven(
    testLocation = "RefundServiceTest",
    coverageGoal = 95,
    framework    = {Framework.JUNIT_5, Framework.ASSERTJ},
    mockPolicy   = "No mocks for the GDS client - use the
                   recorded contract fixtures")
public class RefundService { /* … */ }

Red-Green-Refactor, stated where the code is: the agent must update the matching tests alongside any logic change. coverageGoal is validated at compile time — 150 is a warning, not a surprise in CI.

Two more test-side annotations

@AIParallelTests — strict isolation so the suite survives concurrent execution.
@AIIdempotent — the operation must stay idempotent; the test is how you know.

Keep test rules out of the always-loaded budget

Drop a TESTING.md in the root and test-code guardrails go there instead of into CLAUDE.md — safety annotations still stay inline. For a centralised test module, .vibetags-mirror mirrors the source modules' scoped rules in, globbed to the test sources.

In Spec Kit: ask for tests in /speckit.tasks and they're generated inside each user story's phase, not bolted on as a final phase nobody reaches. Put "we practise TDD" in the constitution and every later phase is judged against it.

Putting it together

A working loop

What I'd actually do on a service here

  • Week 1 — mark the landmines. Six safety annotations only: @AILocked, @AICore, @AIPrivacy, @AIIgnore, @AIAudit, @AISecure. Maybe thirty elements in a service. Opt in to whatever config files the team already has.
  • Week 2 — turn on the gates. Add the check-mode profile and the locked-files Action in warn-only mode. Let it be noisy for a sprint before it blocks.
  • Week 3 — go granular. mkdir .claude/rules .cursor/rules, add .vibetags-root-index, and watch the always-loaded file shrink.
  • Week 4 — one feature through Spec Kit. Something mid-sized. Run the whole chain including clarify, checklist and analyze, with a human sign-off at each. Then compare it honestly against how you'd have done it.
  • Ongoing — annotate on the way past. Every time you explain a constraint in a PR comment, ask whether it should have been an annotation instead.

The test for whether a rule belongs in code

A hand-written AI rule is a constraint somebody wished they could express in code. That's the whole design premise — five of the annotations were reverse-engineered from guardrails real maintainers had written by hand across 225 open-source CLAUDE.md files. Where a hand-written rule had no matching annotation, that was a gap in the library.

It dogfoods itself

ProjectFactsConsistencyTest verifies the 44/37/49/13 counts across the pom, the README badge and the changelog — kept in sync by @AIKeepInSync(enforcedBy = "ProjectFactsConsistencyTest"). AnnotationReferenceTest regenerates the annotation table from source and fails the build if the docs drift.

If the rule can't fail a build, it will eventually be wrong — and nobody will notice.

The whole idea, in one picture

Guardrails, not handcuffs

The goal was never to slow the agent down. It is to make the small number of places where it must not improvise explicit, checkable, and impossible to miss.

Inside the box

Full speed. Refactor, rewrite, generate, optimise. Most of a codebase is not load-bearing, and pretending otherwise just makes the tool useless.

The walls

Six safety annotations inline, per-element detail on demand, a drift check in CI, and a PR guard on locked code. Few, explicit, and enforced by something other than good intentions.

The walls are transparent on purpose: the agent can see what it is not allowed to touch, and why.

Takeaways

Six things to leave with

  • Context is a budget, not a dumping ground. Every line in an always-loaded file competes with the question you actually asked.
  • Safety rules must be present before the mistake, not loaded after the agent opens the file. That's why six annotations stay inline and 38 don't.
  • If it describes the code, store it with the code. Prose in a separate Markdown file has no mechanism that keeps it true.
  • A rule that can't fail a build will eventually be wrong. Check mode and the locked-files guard are the difference between a convention and a constraint.
  • Guardrails and specs are different context. VibeTags for "don't touch this", spec / plan / tasks for "build this". You need both.
  • The gates are the point. Clarify, checklist, analyze and a failing test are all the same move: make the human decision cheap and early.
