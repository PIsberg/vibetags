Same-session allocation comparison — 0.9.5 / 0.9.7 / 1.0.0-RC1 / 1.0.0-RC9
==========================================================================

Why this file exists
--------------------
The per-release `memory.txt` baselines were each captured on the day that release was cut. They
are not comparable to one another at the precision this table needs, and reading them as if they
were produces a confident wrong answer: 1.0.0-RC1's recorded OverheadAlloc at N=1000 is 206937 KB
and 1.0.0-RC9's is 216016 KB, which looks like a 4.4 % regression. It is not one. The *baseline*
column — javac compiling the same sources with no annotation processor at all — moved from
132792 KB to 144388 KB between those two captures. The machine changed, not the processor.

So every row below was measured back-to-back in one session, same JDK, same machine, same working
set, switching only `-Dprocessor.version`. That is the only form of this comparison worth drawing
a chart from.

Method
------
    cd load-tests
    mvn test -Dprocessor.version=<V> -Dtest=MemoryVolumeStressTest -Dstress.max.classes=1000

Version resolution was verified rather than assumed:
    mvn dependency:tree -Dprocessor.version=1.0.0-RC1 | grep vibetags-processor:jar
    -> se.deversity.vibetags:vibetags-processor:jar:1.0.0-RC1:compile

Reading this honestly
---------------------
N=10 is excluded from every chart drawn from this file. Two RC9 runs of the same build produced
2995 KB and 12187 KB for it — a 4x spread. At that size the measurement is JIT warmup and
classloading, not processor cost, and no conclusion drawn from it would survive a third run.

N=100, 500 and 1000 reproduce to within 0.6 % across the two RC9 runs, so differences larger than
about 1 % there are the processor and differences smaller are not.

What the numbers say:
  * RC9 allocates 4.9 % less than 0.9.7 at N=1000, 7.3 % less at N=500, 10.8 % less at N=100.
  * RC9 and RC1 are the same build for this purpose (0.15 % apart at N=1000, inside the noise
    floor). RC9 holds the RC1 optimizations; it does not add to them. Nothing between RC1 and RC9
    claimed an allocation win, so this is the expected result and not a finding.
  * PeakHeap is reported for completeness and is not used for any claim. It depends on when GC
    happened to run; the same RC9 build produced 112 MB and 87 MB at N=500.
